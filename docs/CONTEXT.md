# Project context

## Current state

OpenCode Recovery is a Windows x64 Tauri dashboard for live OpenCode sessions. Version **0.1.0** is a preview candidate. Read the [user guide](USAGE.md) for behavior and the [roadmap](ROADMAP.md) for verified milestones. Source and tests define implementation; this file maps them.

The dashboard lists every live OpenCode tab as a flat row, with the project and the source named on the row itself and the project path in the inspector. The rail groups projects into Orca and other sources. Idle/Working/Rate limited/Provider blocked/Worker Idle/unavailable describe OpenCode activity beneath the title; selected/background describe terminal selection. A row also reports the child sessions still executing, as "2 subagents working". A separate Recovery column shows the app's process, and reads Continued for a session that was already continued for the stop it is on and is now waiting for new operator input. It also covers Stopped · 2-IP limit. Historical session lists and saved global tabs are not discovery sources. Previously observed failures remain visible after closure with no delivery route.

Saved monitoring rules include individual sessions and whole terminals. Session overrides win; new tabs inherit a terminal rule. Each session also follows a watcher mode, rate limits or Worker Idle, chosen for that session or for all sessions, with the session choice winning. The app-wide default is Worker Idle, and the app-wide **Recovery** control in the top bar switches it; a session can stay on **Default** and follow it, or override it. A cached ownership binding preserves exclusions during API fallback. Unchecking prunes queued work. Pausing clears queues, and an epoch guard prevents raced busy receipts from restoring canceled work. Every busy session still protects machine-wide routing, regardless of monitoring selection.

Failed rate-limit/quota events and the specific OpenCode free-tier client-gate provider message can queue recovery. Recovery bounds relay attempts to five, waits up to 20 seconds per connection, requires a connected SoftEther account and changed public IPv4, and limits a session to two verified IP changes. Exact-session plugin requests, claimed receipts, and persisted incident guards avoid uncertain automatic resubmissions. Busy targets can wait on the already verified route. In Worker Idle mode the same machinery runs without the network: a cleanly finished turn queues a prompt only, changes no public IP, and uses none of the two IP changes. Changing a session's mode cancels the other kind of work queued for it, and a manual recovery follows the session's mode. A session is continued once per stop, keyed on the operator's own last message, and only again after new operator input. The stopped-turn state and the child-session count come from the live plugin alone; the shared-service fallback keeps reporting rate limits, busy, and idle only, and never continues a session.

The UI uses the app icon's own green-black enamel for every surface, porcelain ink in three legible steps, hairline rules instead of card borders, and lime reserved for what is live. Each recovering session carries a route line: six stations from Queued to Receipt with the current stage marked, so the fleet's state is readable across rows. A failed, stopped, or uncertain run breaks the line in vermilion, at the station where the run actually stopped. A recovery that changes no IP draws the relay and IP-verification stations as short dashes and breaks the line across them, so the route that was not taken stays visible. The live station breathes while a recovery moves, unless reduced motion is requested. The VPN route bar itself appears only while a relay is connected, a recovery is changing the public IP, or a session waits on a rate-limit recovery, so it disappears when only Worker Idle watching is left; the **Provider errors** filter is hidden on the same condition. Preview fixtures remain development-only. Background CLI helpers use Windows `CREATE_NO_WINDOW`. `DESIGN.md` records that system as durable tokens and guardrails; `src/styles.css` remains the implementation authority.

Per-session recovery progress is exposed as `Snapshot.recovery`, separate from OpenCode activity/selected-tab state. The controller reports queue/wait/connect/verify/send/receipt/stop stages, details, verified IP-change count, timing, and whether that recovery changes the public IP at all. The 30-second Orca gate starts at a confirmed send receipt and is a minimum, not a fixed retry interval; outside sessions have no such gate. The UI uses a spinner only for active connection/delivery work, a static clock for waits, and a retry-eligibility countdown. Exclusions/pause clear queued indicators; ambiguous receipts never appear as success. Persisted attempt counts remain visible after restart; transient stage details are not persisted.

## Integration constraints

- The live plugin reports all open tabs, selected route, service identity, and per-session execution/error state. It also reports a cleanly finished turn, the number of child sessions still executing, and the operator's own last message, so a stop can be identified and continued once. The shared `/api/session/active` endpoint supplies a responding-session fallback, not idle presence. Unknown status must not become Idle.
- V2 reports support shared and private connected clients through their existing SDK. Legacy V1 leases require the current shared PID. Do not discover arbitrary private endpoints or copy credentials.
- Install only `opc-rotate-presence/tui.js` under OpenCode's plugin directory, respecting `OPENCODE_CONFIG_DIR`. Heartbeats refresh every two seconds and expire after eight seconds; presence contains no prompts or credentials.
- Match Orca's `ORCA_PANE_KEY` to `tabId:leafId`, not the PTY ID. Deduplicate by exact session ID, preferring Orca ownership; never suppress an entire directory's outside sessions.
- Address requests to a live exact session/client/service identity. Claim before submitting, persist the incident guard before transport, clean expired requests, and never retry an ambiguous receipt automatically. Do not type prompts into the currently selected terminal tab.
- There is one built-in prompt, "Continue", used by both watcher modes. Migration replaces a prompt saved under the older two-mode design once, and a per-session prompt override wins over the default.
- SoftEther is separately installed. Control only `OPCRotate_` profiles and refuse an unrelated active account. Do not enable monitoring or perform a live VPN test just to inspect the UI.
- Local settings, state, credentials, and generated release files stay outside Git. Source is MIT licensed; preserve third-party notices.

## Verification baseline and gaps

The layout clarification fixes a flex-basis regression that made activity labels 124–128px tall inside a vertical stack. Session rows now use a shared grid with the sticky column header inside the same scroll container. Browser checks verified 72px desktop rows, exact header/recovery-column alignment, longer wrapped titles at the desktop minimum, no horizontal overflow at 1280 × 820, 980 × 660, and 390 × 844, keyboard selection, expandable timing details, monitoring exclusions, and empty search. Inspected non-disabled text contrast passed, and Impeccable's detector returned no findings. Timing and project details use native disclosures; manual retry remains the existing command, relabeled for stopped sessions. The earlier browser verification blocker is resolved for the current tab; no live VPN change was performed.

The recovery-progress update passed **9 Node and 34 Rust tests**, the production frontend build, NSIS packaging, and the release fixture-exclusion check. New tests cover the Orca send-based minimum delay, outside-source timing, per-session progress/counts, exclusion cleanup, saved limits, and stable stage timestamps. Its original browser check was blocked; the current layout verification above supersedes that gap. Live VPN verification remains pending.

The two-watcher-mode update passed **11 Node and 42 Rust tests** and the production frontend build. New coverage includes the watcher precedence, a Worker Idle queue that changes no public IP, one continuation per stop, the exclusion of a rate-limited session in Worker Idle mode, and the necessity of the VPN route. Browser preview checks covered both modes, the inspector's per-session and app-wide controls, the **Worker Idle** activity state, the subagent count, and the route bar's disappearance while nothing depends on the VPN route. The live behavior against a real OpenCode client remains unverified.

The watcher-mode rework renamed the finished-turn mode to **Worker Idle** and made it the app-wide default. The app-wide **Recovery** control sits in the top bar immediately left of the **Monitoring** switch and switches between **Rate limits** and **Worker Idle**; the session inspector offers **Rate limits**, **Worker Idle**, and **Default**, with a line naming the mode the session follows. The persisted `continue` value migrates to `worker-idle` on load. In **Worker Idle** mode the route bar and the **Provider errors** filter are hidden and the inspector action reads **Continue session**; the route line breaks across the two skipped relay stations instead of omitting them, and the live station breathes unless reduced motion is requested. Changing a session's mode cancels the other kind of queued work, and a manual recovery follows the session's mode. The update passed **11 Node and 48 Rust tests** and the production frontend build. The live behavior against a real OpenCode client remains unverified.

A shared OpenCode service that has stopped now reports itself as not running instead of failing the request. A refused connection is treated as a service that is gone, which has no live sessions of its own and therefore cannot block a route change; a service that answers with an error or times out still blocks one. The service is still reached only through the recorded loopback address and password, and the app never hunts for other endpoints.

There is now one continuation prompt. The app used to keep a default per watcher mode, and the editor on screen did not always show the prompt that was sent: the sidebar edited the rate-limit prompt while a **Worker Idle** session received the other one. The default is "Continue", used by both modes, and the session inspector shows the effective prompt with plain wording: "Used by every session" beside **Edit the default**, or "This session's own prompt" beside **Use the default**. The sidebar and the inspector now edit the same prompt. A prompt saved under the older design is replaced once, and a session's own prompt is untouched. The watcher choice in the inspector also stops stacking: the label, the control and the note sit on their own lines, so a mode button cannot stretch. The update passed **11 Node and 48 Rust tests** and the production frontend build.

A stop is only recorded as continued when the prompt was actually delivered. The app used to record it even when the live client could not take the prompt, which left a session that was never continued looking finished, and the record survived a restart while the progress did not. A session that cannot be continued now stays queued, the stage reads **Waiting for client**, the next scan tries again, and the operator can start it by hand. The record of continued stops is cleared once, so a session held by the old behavior is continued again. A session that has already been continued for the stop it is on now says so. The app continues a finished turn once and waits for new operator input, and the interface used to leave that session reading **Worker Idle** beside **Prompt sent**, which looked like an unfinished recovery. The controller marks a session whose stop key has already been handled, the recovery column reads **Continued**, and the inspector explains that the session is continued again after a new message. The waiting text follows the watcher mode instead of always naming provider errors, and the monitoring note states the rule rather than a status that reads as live. The update passed **11 Node and 49 Rust tests** and the production frontend build.

The pre-release baseline passed **9 Node plugin tests and 31 Rust tests**, TypeScript/Vite build, and NSIS packaging. Windows helper coverage verifies no console handle while output is captured. Browser preview checks covered the requested project hierarchy, monitoring controls, keyboard behavior, empty states, desktop sizes, and inspected text contrast. Native checks confirmed live idle/background tabs and the free-tier provider error without triggering recovery.

Earlier live VPN recovery used the former terminal-send transport. **Live continuation using the current exact-session bridge remains unverified**, including Orca, outside clients, and background tabs. Clean-PC install/upgrade/uninstall and IPv6 egress remain open. Signing and automatic updates are not configured. Use the release checklist rather than treating a successful installer build as end-to-end acceptance.

The Windows workflow checks locked dependencies, versions, formatting, tests, npm audit, production fixture exclusion, and NSIS output. It uploads an installer/checksum artifact only; publication is a separate maintainer action.
